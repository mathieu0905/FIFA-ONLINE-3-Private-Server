FO3-001：新增球员后，游戏在出现主界面前崩溃
现象：FC 三卡版 data_0.big 启动后约数秒生成 dump，尚未请求 locale/login。不能归咎于商城或经理存档。
已确认：捕获 dump 的异常为 0xC0000005，EIP 0x005EA97C（模块 RVA 0x001EA97C）；运行时代码先置零再向空指针写 314159，属于主动 fatal/assert 路径，不能当作随机野指针。栈内含 data_0.big 路径。
已确认：原目录 271 项偏移有序。通用 append 补丁把中间目录索引 257（从 0 开始）的 data/db2/fifadb.db.db2 移到末尾，使它与后面条目的目录偏移出现逆序。其余条目仍指向较早位置。
已确认：仅换回原版 data_0.big 后能出现游戏窗口；这只证明对照版通过更早的启动阶段，不代表已经通过登录、经理选择或比赛。
根因证据边界：dump 和布局差异将故障定位到 data0 资源路径；不能仅凭 dump 声称已反编译出具体原生校验条件。随后保持 DB 内容/压缩不变、只修外层布局，原生启动恢复，进一步支持布局兼容性是本次回归的关键因素。
已安装修复：保持原成员顺序、DB 原起点，按新 DB 压缩大小整体顺移后续 14 个成员；其余 270 个压缩 payload 逐字节不变。SQLite 内容与原 FC 新库相同。正式 data0 SHA256 为 42dfbda1f2f3c9b5f322d0de14426dd660982b8133a038c251d7aaa163433b17。
验证状态：2026-11-06 08:52 后正式有序 data0 已通过原生窗口启动、locale/login、原经理 ggmu、进入大厅、进入球员管理并显示 97 人。这不是仅结构通过。FC 三张新卡的逐卡详情、市场、开包和比赛加载仍需分别验收；不能由原经理进入大厅推成这些都完成。
禁止重犯：不要对 data_0.big 的中间成员继续使用“末尾追加再改指针”而跳过原布局检查。不要为此全局改 bigdir.patch，误伤已验证的单成员 UI/语言 BIG。
自动门槛：tools/check_data0_layout.py；原版 PASS、历史 append 坏版因 directory_offset_order FAIL、有序候选 PASS，且除明确允许的 DB 成员外其余压缩数据相同。
实机门槛：无新 native dump → 出现正常窗口 → 收到 locale/login 请求 → 原经理可用 → 新卡列表/详情/市场可用 → 比赛加载。前一项不能代替后一项。
证据：outputs/FO3ID/启动检查/启动崩溃取证.json、data_0-ordered.json、正式data0布局验证.json；outputs/FO3ID/强化20/显示修复/实机验证.json；work/startup_crash/ab-client-baseline.json。布局报告的 native_runtime_verified=false 是检查器本身的能力边界，不应改成 true 来冒充实机检查。
